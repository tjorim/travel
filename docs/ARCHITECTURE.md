# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, visitor-main.tsx   the two entry points (owner app, public/share app); nothing else lives loose in src/
vite-env.d.ts, api-types.ts  ambient types; the single import point for API shapes
app/                    bootstrap and app shell: App.tsx, providers (auth, capture, owner header, query), router (route tree,
                        search params, navigation guard), layout (the error boundary and shell)
features/<domain>/      one folder per business domain: pages, components used only there, hooks, feature-only
                        helpers, types and API calls
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
hooks/                  shared hooks used by two or more features
lib/                    framework-agnostic helpers and the HTTP client (lib/api/); no `utils/` folder
mocks/                  MSW server, handlers and fixtures (fixtures are typed with the generated API types)
i18n/                   Paraglide glue: the locale context and the content language
types/                  UI-only types (never API shapes); not needed yet
config/                 runtime configuration and constants; not needed yet
styles/                 global CSS (app.css, tailwind.css)
paraglide/              compiled messages (generated, git-ignored)
api-schema/             generated by Orval, never edited
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area (`features/trips/` does: 17 sub-areas, the largest has 24 files).
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/trips/records/visibility`); use relative imports only inside
  one feature folder (at most one `../`), or between files of the same folder.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/trips/trip/Trips.tsx` is covered by
  `tests/features/trips/trip/Trips.test.tsx`). Shared helpers are in `tests/utils/` and are imported relatively; global
  setup is `tests/setup.ts`. End-to-end specs are in `frontend/e2e/`.

### Frontend audiences

- **Owner-only.** The owner entry (`main.tsx`), app shell and providers (`app/`), owner feature modules and authenticated
  API requests (`lib/api/owner-api.ts`). This includes private record editors, offline copies, owner queries, session
  helpers and the preview controls that fetch projections for the owner.
- **Visitor-only.** The visitor entry (`visitor-main.tsx`) and `features/visitor/` hold the landing, public and unlisted
  routes and the saved shared-link store.
- **Shared.** Both audiences can use the projection renderer and map, design-system primitives, locale and preference
  controls, generated API types and API error handling (`lib/api/api.ts`). The owner preview fetches its projection in
  `features/trips/publication/RenderedPreview.tsx` and passes the result to the shared renderer.

Visitor entries and visitor route modules must never import owner-only code, directly or transitively. Shared modules
used by visitors follow the same rule. Keep new owner-only feature code in its feature folder. For owner-only helpers
outside those folders, use an `owner-` or `Owner…` filename or register the path in `scripts/visitor-imports.mjs`
when an existing naming convention requires a different name.

`pnpm lint` checks this boundary from `visitor-main.tsx` and every source module in `features/visitor/`. It follows
local imports, re-exports, type-only imports and literal lazy imports, and reports the chain that reaches a restricted
module. Use explicit imports in this graph so each dependency can be checked. The generated API schemas and Paraglide
output are treated as leaves.

### File size

Keep a frontend source file under 650 lines. Past that, split by responsibility (a hook for state and effects, a module
for pure helpers, one component per section) instead of growing the file. A file may exceed the limit only with a
reason recorded here; none do today, and the largest are `CaptureDialog.tsx` (637), `PublicationManager.tsx` (597) and
`MediaManager.tsx` (590). The limit is a review rule, not a lint check.

### Folder layout

Visitor, owner and shared code is separated by the import boundary above, not by top-level `visitor/`, `owner/` and
`shared/` folders. Moving files would not make the rule any stronger, since the check follows imports whatever the
folder, and it would churn every import path. Revisit the folders only if the boundary check stops being enough.

### Exceptions

- `src/main.tsx` and `src/visitor-main.tsx` both stay at the top of `src/`. `index.html` loads `main.tsx` (the owner app
  under `/admin/`); `landing.html`, `public.html` and `share.html` load `visitor-main.tsx` (the public `/trips/` and
  unlisted `/share/` views, routed by the visitor plugin in `vite.config.ts`). Moving them would mean editing the HTML
  pages and the Vite inputs for no gain.
- Names were kept as they were so that every move is a pure `git mv`: module files are kebab-case (`agenda-items.ts`,
  `use-open-sections.ts`) next to a few camelCase hooks, and the route components keep their names (`Trips.tsx`,
  `TripWorkspace.tsx`, `Capture.tsx`) instead of a `*Page.tsx` suffix. New files follow the shared convention
  (`PascalCase.tsx` components, `useThing.ts` hooks, `camelCase.ts` modules).
- `components/projection/` is the visitor view of a trip (`ProjectionView`, the header, numbers and current locations). It serves both
  the visitor app and the owner's previews.
- Owner code reads `useAuth` from `app/providers/auth-context`. Both audiences read `useLocale` from `i18n/locale`.
- Features are independent except for these deliberate links: `app/` composes the pages of every feature;
  `features/sharing/` reuses the scope editor, link lifecycle, catalog and preview controls of `features/trips/publication/`, which in turn
  reads the member types of `features/sharing/collections`; `features/library/` embeds the document manager and the
  packing list view; `features/trips/workspace/` embeds the document manager. Anything else two features need goes to a
  shared folder.
- `lib/` has sub-folders by topic: `api/` (HTTP calls, feedback errors and error messages), `query/` (query client, keys
  and the owner queries) and `map/` (map style, messages, errors and route geometry).
- `src/mocks/fixture-contracts.typecheck.ts` imports from `e2e/` and `tests/utils/`, so it uses relative paths.
- Decision records under `docs/decisions/` name source files as they were when the decision was written; they are not
  rewritten when files move.

## Where does new code go?

- A new owner page or screen: `features/<domain>/<Name>.tsx`, lazy-loaded in `app/App.tsx` and registered in
  `app/router/router.tsx`. A new visitor route: `features/visitor/visitor-routes.tsx`.
- A component only one feature uses: that feature's folder. A second feature needs it: `components/`.
- A design-system primitive (a Base UI / shadcn wrapper): `components/ui/`, recorded in `ui-maintenance.json`.
- A hook or helper only one feature uses: that feature's folder. Shared: `hooks/` or `lib/<topic>/`.
- An API call or query key: next to the feature that owns it; shared ones go to `lib/api/` and `lib/query/`.
- A provider, router change or layout piece: `app/`. A message or locale helper: `i18n/`.
- MSW handlers and fixtures: `mocks/`. Global CSS: `styles/`.
- A test: `tests/` at the same path as the file it covers; a test helper: `tests/utils/`.

## Backend (`backend/app/`)

```
main.py                 app assembly: middleware, router registration, lifespan; nothing else
mcp_server.py           the stdio MCP entry point (`python -m app.mcp_server`): re-exports `app.mcp`, see "Entry points"
openapi_export.py      writes frontend/openapi.json (`uv run python -m app.openapi_export`)
version.py              the release version read from /VERSION
routers/                the HTTP layer, one module per domain; thin: validate, call a service, return a response model
services/               business logic shared by the routers and the MCP tools; a service never commits (the transport does)
  sharing/              what each audience receives: audience, audiences, access, exclusions, precision, projection,
                        publication, hidden-link service, presets, delivery, link preview, overview, visitor changes
  media/                owner media service, ingestion pipeline, providers, OAuth, range delivery, the apps media worker
  documents/            owner document service and ingestion
  places/               owner place-search service, OSM search, navigation targets, country names
  audit, export, maintenance, pdf_renderer, route_overlap, storage, storage_reconcile, task_alerts, track_import,
  translation, trip_pdf, update_zones   single-module domains; the other `<domain>.py` files are the owner operations
                        per record kind (trips, areas, locations, stays, routes, visits, alternatives, packing, tasks, ...)
models/                 SQLAlchemy models, one module per domain; `enums.py` has every closed vocabulary, `base.py` the
                        opaque id and column factories; `__init__` imports every module (Alembic needs them all)
schemas/                Pydantic request and response models, one module per domain; `base.py` has InputModel/ResponseModel
core/                   settings, errors, bearer auth, failed-auth and visitor rate limits, request limits, capability
                        tokens, provider secrets, content-language and update-day rules, markdown and search helpers
db/                     engine and session (`session.py`), the declarative base (`base.py`), the SQLite dev schema helper
mcp/                    the owner MCP server: one module per tool family (trips, itinerary, places, sharing, collections,
                        media, documents, packing, tasks, alternatives) plus the backend, rendering and server assembly
middleware/             ASGI middleware (Server-Timing and slow-request log)
```

Tests live in `backend/tests/` and mirror this tree (`tests/routers`, `tests/services`, `tests/core`, `tests/db`,
`tests/middleware`, `tests/schemas`, `tests/mcp`); `conftest.py`, `golden/` and `legacy_rows.py` are shared. The
`*_postgres` and migration tests (they find `alembic/` relative to `tests/`), the golden-file tests and the cross-cutting
tests (error contract, OpenAPI snapshot, architecture scans, the Python client) stay at the top. Sibling-test imports are
package imports (`from tests.routers.test_publication import ...`).

Rules: every JSON route declares a response model; routers do not touch the database directly and do not import each
other; a service never imports a router; code used by one domain stays in that domain's modules. Dependencies point
downwards: `routers` and `mcp` -> `services` -> `schemas`, `models` -> `core`, `db`. `core` and `db` never import
`services`, `schemas`, `routers` or `mcp`; the two upward edges are `core/secrets.py` (reads the provider secrets table
through `models`) and `db/dev_schema.py` (imports `models` to register every table), and `models` imports only `core`
and `db`. Package `__init__` files in `services/` are docstring-only, so importing one module never loads a sibling.

Naming: inside a sub-package, `service.py` is the owner-facing service of the domain (the old `services/<name>.py`) and
`ingest.py` the copy-verify-record pipeline. Schemas and models are named after the domain, not the record
(`schemas/stays.py`, `models/stays.py`). `from app.models import X` and `from app.schemas import X` keep working through
the package re-exports (explicit `__all__`); new code may import the submodule. Models that refer to each other only in
annotations import each other under `TYPE_CHECKING` (the module files use `from __future__ import annotations`).

### Where does new backend code go?

- A new endpoint: `routers/<domain>.py` (thin), its operation in `services/<domain>.py` (or the domain's sub-package),
  request/response models in `schemas/<domain>.py`, tables in `models/<domain>.py` plus an Alembic revision; add the
  new model module to `models/__init__.py`, the schemas to `schemas/__init__.py`.
- An MCP tool: `mcp/<family>.py`, calling the same service the router calls; never a second implementation.
- Something every domain needs and that knows nothing of a domain (settings, errors, limits, auth): `core/`.
- Something that reads or writes the engine, session or dev schema: `db/`. ASGI plumbing: `middleware/`.

### Entry points kept at their old path

These modules only forward to the code in the new layout, because commands documented for operators and MCP clients start
them by name. Each can go once the units that call them have moved to the new module path.

| Old path | Forwards to | Used by | Removal |
| --- | --- | --- | --- |
| `app/mcp_server.py` | `app.mcp` | `python -m app.mcp_server` (docs, MCP client configs), `from app.mcp_server import ...` | when MCP client configs use `python -m app.mcp` |
| `app/maintenance.py` | `app.services.maintenance` | `python -m app.maintenance` (docs/object-storage.md, systemd timers) | when the timers use the new path |
| `app/task_alerts.py` | `app.services.task_alerts` | `python -m app.task_alerts` (VPS scheduler, backend/README.md) | when the scheduler uses the new path |
| `app/media/worker.py` | `app.services.media.worker` | `python -m app.media.worker` (supervised dispatcher, docs/media-worker.md) | when the service unit uses the new path; delete `app/media/` with it |

`python -m app.dev_schema` is now `python -m app.db.dev_schema` (a development-only command, no shim). Logger names that
come from `__name__` follow the module (for example `app.middleware.request_timing`, `app.services.translation`); the
literal logger `app.mcp_server` is unchanged.
