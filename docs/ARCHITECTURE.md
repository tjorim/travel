# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, visitor-main.tsx   the two entry points (owner app, public/share app); nothing else lives loose in src/
vite-env.d.ts, api-types.ts  ambient types; the single import point for API shapes
app/                    bootstrap and app shell: App.tsx, providers (auth, capture, owner header, query), router (route tree,
                        search params, navigation guard), layout (the error boundary and shell)
features/<domain>/      one folder per business domain: pages, components used only there, hooks, feature-only
                        helpers, types and API calls
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
hooks/                  shared hooks used by two or more features
lib/                    framework-agnostic helpers and the HTTP client (lib/api/); no `utils/` folder
mocks/                  MSW server, handlers and fixtures (fixtures are typed with the generated API types)
i18n/                   Paraglide glue: the locale context and the content language
types/                  UI-only types (never API shapes); not needed yet
config/                 runtime configuration and constants; not needed yet
styles/                 global CSS (app.css, tailwind.css)
paraglide/              compiled messages (generated, git-ignored)
api-schema/             generated by Orval, never edited
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area (`features/trips/` does: 17 sub-areas, the largest has 24 files).
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/trips/records/visibility`); use relative imports only inside
  one feature folder (at most one `../`), or between files of the same folder.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/trips/trip/Trips.tsx` is covered by
  `tests/features/trips/trip/Trips.test.tsx`). Shared helpers are in `tests/utils/` and are imported relatively; global
  setup is `tests/setup.ts`. End-to-end specs are in `frontend/e2e/`.

### Exceptions

- `src/main.tsx` and `src/visitor-main.tsx` both stay at the top of `src/`. `index.html` loads `main.tsx` (the owner app
  under `/admin/`); `landing.html`, `public.html` and `share.html` load `visitor-main.tsx` (the public `/trips/` and
  unlisted `/share/` views, routed by the visitor plugin in `vite.config.ts`). Moving them would mean editing the HTML
  pages and the Vite inputs for no gain.
- Names were kept as they were so that every move is a pure `git mv`: module files are kebab-case (`agenda-items.ts`,
  `use-open-sections.ts`) next to a few camelCase hooks, and the route components keep their names (`Trips.tsx`,
  `TripWorkspace.tsx`, `Capture.tsx`) instead of a `*Page.tsx` suffix. New files follow the shared convention
  (`PascalCase.tsx` components, `useThing.ts` hooks, `camelCase.ts` modules).
- `components/projection/` is the visitor view of a trip (`ProjectionView`, the header, numbers and current locations,
  `RenderedPreview`). The public app renders it and so do the owner's previews, so it is a shared folder rather than part
  of `features/visitor/`. `features/visitor/` holds the visitor routes and the saved-link store.
- Shared layers read two contexts that live in `app/` and `i18n/`: `useAuth` (`app/providers/auth-context`) and
  `useLocale` (`i18n/locale`).
- Features are independent except for these deliberate links: `app/` composes the pages of every feature;
  `features/sharing/` reuses the scope editor, link lifecycle and catalog of `features/trips/publication/`, which in turn
  reads the member types of `features/sharing/collections`; `features/library/` embeds the document manager and the
  packing list view; `features/trips/workspace/` embeds the document manager. Anything else two features need goes to a
  shared folder.
- `lib/` has sub-folders by topic: `api/` (HTTP calls, feedback errors and error messages), `query/` (query client, keys
  and the owner queries) and `map/` (map style, messages, errors and route geometry).
- `src/mocks/fixture-contracts.typecheck.ts` imports from `e2e/` and `tests/utils/`, so it uses relative paths.
- Decision records under `docs/decisions/` name source files as they were when the decision was written; they are not
  rewritten when files move.

### Features

| Folder                      | What it holds                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| `auth`                      | the OIDC callback page (`/auth/callback`); the session helpers are in `lib/auth.ts`                     |
| `documents`                 | the document manager (booking, itinerary, receipt files) used by the library and by trips               |
| `library`                   | the library page: emergency info, offline copies of documents and packing lists                         |
| `settings`                  | the settings page                                                                                      |
| `sharing`                   | the sharing overview, collections and their members                                                    |
| `visitor`                   | the public and unlisted visitor routes and the saved shared-trip links                                  |
| `trips/trip`                | the owner home and the trips list, trip card, editor, cover, language, export and PDF, state helpers   |
| `trips/workspace`           | the trip workspace: header, tabs, navigation, search, the Plan/Prepare/Story/Sharing/Packing sections, owner map |
| `trips/detail`              | the read-only trip detail page and its record blocks                                                   |
| `trips/capture`             | quick capture: page, dialog, draft store, photos, place search                                         |
| `trips/agenda`, `tasks`, `updates` | the day agenda, trip tasks and the travel-update story                                          |
| `trips/records`             | plumbing shared by the record editors: actions, mutations, focus, visibility, merge, place picker, form fields |
| `trips/areas`, `locations`, `routes`, `stays`, `visits`, `alternatives` | one folder per record kind (details, form, editor, model, mutations) |
| `trips/media`               | media assets and copies, import, candidate review                                                      |
| `trips/packing`             | packing lists, bags, items, templates, departure check                                                 |
| `trips/publication`         | public and unlisted links, presets, exclusions, audit, live location                                   |

## Where does new code go?

- A new owner page or screen: `features/<domain>/<Name>.tsx`, lazy-loaded in `app/App.tsx` and registered in
  `app/router/router.tsx`. A new visitor route: `features/visitor/visitor-routes.tsx`.
- A component only one feature uses: that feature's folder. A second feature needs it: `components/`.
- A design-system primitive (a Base UI / shadcn wrapper): `components/ui/`, recorded in `ui-maintenance.json`.
- A hook or helper only one feature uses: that feature's folder. Shared: `hooks/` or `lib/<topic>/`.
- An API call or query key: next to the feature that owns it; shared ones go to `lib/api/` and `lib/query/`.
- A provider, router change or layout piece: `app/`. A message or locale helper: `i18n/`.
- MSW handlers and fixtures: `mocks/`. Global CSS: `styles/`.
- A test: `tests/` at the same path as the file it covers; a test helper: `tests/utils/`.

## Backend (`backend/app/`)

The backend keeps its current layout for now (flat modules such as `models.py` and `schemas.py` next to `routers/`,
`services/`, `mcp_server/`, `media/` and `places/`). The shared target,
applied to all four apps in a later step, is `main.py`, `core/`, `db/`, `models/`, `schemas/`, `routers/`, `services/`,
`mcp/` and `middleware/`.
